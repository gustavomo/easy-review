# Phase 02.1: In-Editor PR Navigation - Research

**Researched:** 2026-04-03
**Domain:** VS Code TreeDataProvider hierarchy, TextDocumentContentProvider, GitHub REST API, React webview panels
**Confidence:** HIGH

## Summary

Phase 02.1 replaces the `vscode.env.openExternal` stub with full in-editor PR navigation. The work has three distinct sub-problems: (1) evolving the flat `EasyReviewPRsProvider` into a three-level tree (PR → directory → file), (2) implementing a `TextDocumentContentProvider` for the `easy-review-diff://` URI scheme that fetches file content from GitHub REST API on demand, and (3) adding a lightweight PR overview webview panel that reuses the existing React/Vite webview infrastructure from Phase 2.

All integration points already exist: the Octokit access pattern is established in `activation.ts` (`credentialStore.getHub(AuthProvider.github).octokit.api`), the GitHub API calls follow the same pattern as `DiffFetcher.ts` and `AllStatesPRFetcher.ts`, and the webview panel structure follows the `ReviewPanel.ts` singleton template exactly. No new libraries are required — this phase is pure TypeScript/VS Code API work within the established stack.

The highest-complexity decision is the `EasyReviewPRsProvider` refactor: the provider must support a union type `PRNode | DirectoryNode | FileNode` and route `getChildren()` differently for each type. The `DirectoryTreeNode` algorithm from the upstream fork (compact single-child dirs, sort dirs before files) is the reference implementation to port.

**Primary recommendation:** Port the upstream `DirectoryTreeNode` algorithm as a standalone `buildDirectoryTree()` function that operates on `PRFileChange[]` — no inheritance from `TreeNode`, no dependency on `PullRequestModel`. Wire it into a `EasyReviewTreeNode` union type that `EasyReviewPRsProvider` uses for its generic parameter.

### Pattern 1: EasyReviewTreeNode Union Type

The provider's generic parameter changes from `PRTreeItem` to `EasyReviewTreeNode`:

```typescript
// EasyReviewTreeNodes.ts
export type EasyReviewTreeNode =
  | PRTreeItem
  | DirectoryNode
  | FileNode
  | LoadingNode
  | ErrorNode;

export class DirectoryNode extends vscode.TreeItem {
  readonly kind = 'directory' as const;
  constructor(
    public readonly label: string,
    public children: EasyReviewTreeNode[],
  ) {
    super(label, vscode.TreeItemCollapsibleState.Expanded);
    this.iconPath = new vscode.ThemeIcon('folder');
  }
}

export class FileNode extends vscode.TreeItem {
  readonly kind = 'file' as const;
  constructor(
    public readonly file: PRFileChange,
    public readonly pr: StoredPR,
  ) {
    super(file.filename.split('/').pop() ?? file.filename, vscode.TreeItemCollapsibleState.None);
    this.iconPath = FILE_STATUS_ICON[file.status]; // ThemeIcon per status
    this.description = file.filename;
    this.command = {
      command: 'easy-review.openFileDiff',
      title: 'Open File Diff',
      arguments: [pr, file],
    };
  }
}

export class LoadingNode extends vscode.TreeItem {
  readonly kind = 'loading' as const;
  constructor() {
    super('Loading files...', vscode.TreeItemCollapsibleState.None);
    this.iconPath = new vscode.ThemeIcon('loading~spin');
  }
}

export class ErrorNode extends vscode.TreeItem {
  readonly kind = 'error' as const;
  constructor(public readonly pr: StoredPR) {
    super('Failed to load files — click to retry', vscode.TreeItemCollapsibleState.None);
    this.iconPath = new vscode.ThemeIcon('error', new vscode.ThemeColor('errorForeground'));
    this.command = {
      command: 'easy-review.retryLoadFiles',
      title: 'Retry',
      arguments: [pr],
    };
  }
}
```

### Pattern 2: EasyReviewPRsProvider with Async getChildren

**Critical insight:** `TreeDataProvider.getChildren()` can return a `Promise` — VS Code will show the loading spinner automatically if the provider fires `onDidChangeTreeData` after async resolution, but the simplest approach is to fire immediately with a `LoadingNode`, then replace with actual nodes once loaded.

```typescript
// EasyReviewPRsProvider.ts (refactored)
export class EasyReviewPRsProvider
  implements vscode.TreeDataProvider<EasyReviewTreeNode>
{
  private _onDidChangeTreeData =
    new vscode.EventEmitter<EasyReviewTreeNode | undefined | null | void>();
  readonly onDidChangeTreeData = this._onDidChangeTreeData.event;

  private prs: PRTreeItem[] = [];
  // Cache: prKey → children (to avoid re-fetch on collapse/expand)
  // D-06: no caching in 2.1 — this map is cleared on each expansion
  private fileCache = new Map<string, EasyReviewTreeNode[]>();

  getTreeItem(element: EasyReviewTreeNode): vscode.TreeItem {
    return element;
  }

  getChildren(element?: EasyReviewTreeNode): vscode.ProviderResult<EasyReviewTreeNode[]> {
    if (!element) {
      // Root: return PR items
      return this.prs;
    }
    if (element instanceof PRTreeItem) {
      // Expansion: fetch file list
      // Return loading node immediately, then trigger async load
      this.loadFilesForPR(element.pr);
      return [new LoadingNode()];
    }
    if (element instanceof DirectoryNode) {
      return element.children;
    }
    // FileNode, LoadingNode, ErrorNode have no children
    return [];
  }

  private async loadFilesForPR(pr: StoredPR): Promise<void> {
    // ... fetches files, builds tree, fires onDidChangeTreeData(prTreeItem)
  }
}
```

**Important:** Firing `onDidChangeTreeData(specificNode)` refreshes only that subtree — not the full tree. The provider must hold a reference to the specific `PRTreeItem` instance to fire correctly.

**Alternative approach (simpler):** Store `children: EasyReviewTreeNode[] | undefined` on `PRTreeItem` itself, then in `getChildren()`: if `undefined`, start async load and return `[new LoadingNode()]`; otherwise return the stored children. Fire `onDidChangeTreeData(prTreeItem)` when loaded.

### Pattern 4: Directory Tree Algorithm (ported from upstream DirectoryTreeNode)

The upstream `DirectoryTreeNode.addFile()` / `addPathRecc()` pattern can be ported as a pure function with no VS Code class dependencies. Key behaviors to preserve:
- **Compact single-child dirs:** `a/b/` with only one subdirectory merges to `a/b` label
- **Sort:** directories before files, both alphabetically
- **Root flattening:** if root `DirectoryNode` label ends up empty, pull children up to avoid a blank root node

```typescript
// directoryTree.ts
export interface PRFileChange {
  filename: string;   // full path, e.g. "src/foo/bar.ts"
  status: 'added' | 'modified' | 'removed' | 'renamed';
  previous_filename?: string;  // for renamed files
  sha: string;        // head blob SHA
}

export function buildDirectoryTree(
  files: PRFileChange[],
  pr: StoredPR,
): EasyReviewTreeNode[] {
  const root = new DirectoryNode('', []);
  for (const file of files) {
    addFileToTree(root, file.filename.split('/'), file, pr);
  }
  compactSingleChildDirs(root);
  sortTree(root);
  // Flatten root if it has the empty label
  return root.label === '' ? root.children : [root];
}
```

### Pattern 5: TextDocumentContentProvider for easy-review-diff://

`vscode.workspace.registerTextDocumentContentProvider(scheme, provider)` registers a provider that VS Code calls when any document with that scheme is opened. The `provideTextDocumentContent(uri, token)` method receives the full URI and must return the file content as a string.

```typescript
// EasyReviewDiffProvider.ts
export class EasyReviewDiffProvider
  implements vscode.TextDocumentContentProvider
{
  private _onDidChange = new vscode.EventEmitter<vscode.Uri>();
  readonly onDidChange = this._onDidChange.event;

  constructor(private readonly credentialStore: CredentialStore) {}

  async provideTextDocumentContent(
    uri: vscode.Uri,
    _token: vscode.CancellationToken,
  ): Promise<string> {
    const { owner, repo, ref, path } = decodeDiffUri(uri);
    // Handle deleted files (no content at head)
    if (ref === 'DELETED') { return ''; }
    const hub = this.credentialStore.getHub(AuthProvider.github);
    if (!hub) { throw new Error('Not signed in to GitHub.'); }
    const octokit = hub.octokit.api;
    const response = await (octokit as any).rest.repos.getContent({
      owner, repo, path, ref,
    });
    // GitHub API returns content as base64-encoded string
    const data = response.data as { content?: string; encoding?: string };
    if (data.encoding === 'base64' && data.content) {
      return Buffer.from(data.content.replace(/\n/g, ''), 'base64').toString('utf-8');
    }
    return data.content ?? '';
  }
}
```

### Pattern 6: URI Encoding for easy-review-diff://

```typescript
// diffUri.ts
export function encodeDiffUri(
  owner: string,
  repo: string,
  ref: string,   // SHA or 'DELETED' for deleted files
  filePath: string,
  label: string, // human-readable for the diff editor title
): vscode.Uri {
  return vscode.Uri.from({
    scheme: 'easy-review-diff',
    authority: `${owner}+${repo}`,  // owner/repo encoded as authority (no slash)
    path: '/' + filePath,           // file path as URI path
    query: `ref=${encodeURIComponent(ref)}&label=${encodeURIComponent(label)}`,
  });
}

export function decodeDiffUri(uri: vscode.Uri): {
  owner: string; repo: string; ref: string; path: string; label: string;
} {
  const [owner, repo] = uri.authority.split('+');
  const path = uri.path.slice(1); // remove leading /
  const params = new URLSearchParams(uri.query);
  return {
    owner, repo,
    ref: decodeURIComponent(params.get('ref') ?? ''),
    path,
    label: decodeURIComponent(params.get('label') ?? ''),
  };
}
```

**Opening the diff editor:**
```typescript
const baseUri = encodeDiffUri(owner, repo, baseSha, file.filename,
  `${file.filename} (base)`);

  `${file.filename} (head)`);
const title = `#${pr.prNumber} ${file.filename.split('/').pop()}`;

```

### Pattern 7: GitHub REST API for File List and Content

**File list** (`/pulls/{number}/files`):
```typescript
const response = await (octokit as any).rest.pulls.listFiles({
  owner, repo, pull_number: prNumber,
  per_page: 100, // PRs with >100 files need pagination
});
// response.data: Array of { filename, status, sha, additions, deletions, ... }
```

**File content** (`/repos/{owner}/{repo}/contents/{path}?ref={sha}`):
- Returns `{ content: string, encoding: 'base64' }` for text files
- Returns `{ content: '', encoding: 'none' }` for files too large (>1MB) — handle gracefully
- For **deleted files** at `head`: the file doesn't exist at the head SHA — use empty string
- For **added files** at `base`: the file doesn't exist at the base SHA — use empty string
- For **renamed files**: `previous_filename` is the base path, `filename` is the head path

**Base/Head SHA extraction from `StoredPR.raw`:**
```typescript
const rawPR = JSON.parse(pr.raw);
const baseSha = rawPR.base?.sha;   // base branch commit SHA
const headSha = rawPR.head?.sha;   // PR head commit SHA
```
The full GitHub API pull request response includes `base.sha` and `head.sha` at the top level — this is confirmed by `PRPersistenceService.ts` which stores `JSON.stringify(fetched.raw)` where `fetched.raw` is the full Octokit `pulls.get` response data.

### Anti-Patterns to Avoid

- **Using `PullRequestModel` or `InMemPRFileSystemProvider`:** Requires the full `FolderRepositoryManager` stack. `StoredPR` cannot feed these — confirmed by CONTEXT.md D-09.
- **Async getChildren returning a Promise:** VS Code does support `Promise` from `getChildren()`, but the loading-node-then-fire pattern gives more control over the loading UX (D-05 requires the `loading~spin` icon explicitly).
- **Using the slash `/` directly in URI authority:** VS Code's URI parser treats `authority` differently from `path`. Encode owner/repo in authority as `owner+repo` (not `owner/repo`).
- **Fetching base content for added files:** Added files have no content at base SHA — return empty string. Missing this causes a 404 that surfaces as a diff provider error.
- **Not handling files > 1MB:** GitHub API returns `encoding: 'none'` and empty `content` for files too large. The provider should return a placeholder message string instead of crashing.
- **Forgetting `provideTextDocumentContent` is called for every URI open:** The provider must be efficient. A simple in-memory cache keyed by URI string is worth adding to avoid double-fetching when VS Code opens both sides of a diff.
- **Not registering the TextDocumentContentProvider in `activateEasyReview`:** Registration must happen in the activation function and the returned `Disposable` must be pushed to `context.subscriptions`.

## Common Pitfalls

### Pitfall 1: PRTreeItem collapsibleState vs command interaction

**What goes wrong:** Setting `CollapsibleState.Collapsed` AND a `command` on the same TreeItem. In VS Code, when a tree item has children AND a command, clicking the label runs the command, but a double-click or expand-arrow click toggles the tree. If you set `CollapsibleState.None` the item becomes non-expandable (current bug).

**Why it happens:** The current `PRTreeItem` was built with `CollapsibleState.None` for the flat list. Changing to `Collapsed` alone doesn't give children — `getChildren(element)` must return non-empty results for that element.

**How to avoid:** Change `PRTreeItem` to `CollapsibleState.Collapsed` AND ensure `EasyReviewPRsProvider.getChildren(prTreeItem)` returns at minimum `[new LoadingNode()]`. The tree won't show the expand arrow unless `getChildren` returns at least one child.

**Warning signs:** PR items show as non-expandable (no arrow) even after setting `Collapsed`.

### Pitfall 2: onDidChangeTreeData fires the wrong element

**What goes wrong:** Firing `_onDidChangeTreeData.fire(undefined)` refreshes the entire tree, collapsing all expanded nodes. After an async file load completes, you only want to refresh the one PR's subtree.

**Why it happens:** `undefined` signals "full refresh." The correct call is `_onDidChangeTreeData.fire(specificPRTreeItem)` to refresh only that node.

**How to avoid:** Hold a reference to the `PRTreeItem` instance when starting the async load. Fire with that specific instance when done. The provider must use a stable reference (same object instance) — not create a new `PRTreeItem` for the fire call.

### Pitfall 3: GitHub API 404 for base content of added files / head content of deleted files

**What goes wrong:** `GET /repos/{owner}/{repo}/contents/{path}?ref={sha}` returns 404 for files that don't exist at that commit. Added files have no base content; deleted files have no head content.

**Why it happens:** The `listFiles` API reports change status but the content fetch doesn't know about it.

**How to avoid:** Check `file.status` before fetching. Return `''` for:
- `status === 'added'` at base ref
- `status === 'removed'` at head ref
For `status === 'renamed'`: use `file.previous_filename` for the base fetch.

### Pitfall 4: URI path encoding collisions

**What goes wrong:** File paths like `src/foo/bar.ts` contain `/` which VS Code interprets as URI path segments. If not carefully encoded, `decodeDiffUri` returns the wrong path.

**Why it happens:** `vscode.Uri.from({ path: '/src/foo/bar.ts' })` is fine — the leading `/` is expected in URI paths. The file path after the leading slash is preserved correctly.

**How to avoid:** Always prefix the file path with `/` in the URI path field. In `decodeDiffUri`, slice off the leading `/` with `uri.path.slice(1)`.

### Pitfall 5: files > 100 in a single API page

**What goes wrong:** `/pulls/{number}/files` is paginated with a default of 30 and maximum of 100 per page. PRs with more than 100 files silently show only the first page.

**Why it happens:** The Octokit call doesn't auto-paginate unless using `octokit.paginate()`.

**How to avoid:** Either use `octokit.paginate('GET /repos/{owner}/{repo}/pulls/{pull_number}/files', ...)` for full pagination, or set `per_page: 100` and add a note that pagination is deferred. For Phase 2.1, `per_page: 100` with a note is acceptable — D-06 explicitly defers caching.

### Pitfall 6: Vite entry point not registered for PR overview

**What goes wrong:** `PROverviewPanel.ts` references `dist/webview/prOverview.js` but that file isn't built because `vite.webview.config.ts` only has one input.

**How to avoid:** Add the second entry to `rollupOptions.input` in `vite.webview.config.ts`:
```typescript
input: {
  webview: 'src/webview/index.tsx',
  prOverview: 'src/webview/prOverview.tsx',
},
output: {
  entryFileNames: '[name].js',  // produces webview.js + prOverview.js
  ...
}
```

### Opening a diff from a FileNode command

```typescript
// Command handler in activation.ts
vscode.commands.registerCommand(
  'easy-review.openFileDiff',
  async (pr: StoredPR, file: PRFileChange) => {
    const rawPR = JSON.parse(pr.raw);
    const baseSha: string = rawPR.base?.sha ?? '';
    const headSha: string = rawPR.head?.sha ?? '';
    const [owner, repo] = pr.repoId.split('/');
    const filename = file.filename.split('/').pop() ?? file.filename;
    const title = `#${pr.prNumber} ${filename}`;

    // For deleted files: use 'DELETED' sentinel so provider returns ''
    const baseRef = file.status === 'added' ? 'EMPTY' : baseSha;
    const headRef = file.status === 'removed' ? 'EMPTY' : headSha;
    // For renamed: fetch base using previous_filename
    const basePath = file.status === 'renamed' && file.previous_filename
      ? file.previous_filename
      : file.filename;

    const baseUri = encodeDiffUri(owner, repo, baseRef, basePath, `${filename} (base)`);
    const headUri = encodeDiffUri(owner, repo, headRef, file.filename, `${filename} (head)`);

    await vscode.commands.executeCommand('vscode.diff', baseUri, headUri, title);
  }
)
```

### Fetching PR files from GitHub

```typescript
// PRFileFetcher.ts
export interface PRFileChange {
  filename: string;
  status: 'added' | 'modified' | 'removed' | 'renamed' | 'copied' | 'changed' | 'unchanged';
  previous_filename?: string;
  sha: string;
}

export async function fetchPRFiles(
  octokit: any,
  owner: string,
  repo: string,
  prNumber: number,
): Promise<PRFileChange[]> {
  const response = await octokit.rest.pulls.listFiles({
    owner, repo, pull_number: prNumber,
    per_page: 100,
  });
  return response.data.map((f: any) => ({
    filename: f.filename,
    status: f.status,
    previous_filename: f.previous_filename,
    sha: f.sha,
  }));
}
```

## Open Questions

1. **Pagination for large PRs (> 100 files)**
   - What we know: GitHub API returns max 100 files per page; Octokit has `paginate()` helper
   - What's unclear: Is `octokit.paginate()` available on the `LoggingOctokit` wrapper from upstream?
   - Recommendation: Use `per_page: 100` for Phase 2.1 and add a comment. If `LoggingOctokit` blocks `paginate`, use `per_page: 100` as the limit. The CONTEXT.md defers caching so pagination complexity is out of scope.

2. **PROverviewPanel singleton vs multi-instance**
   - What we know: D-14 says it opens in ViewColumn.Two; ReviewPanel is singleton
   - What's unclear: Should clicking multiple PRs replace the same overview panel, or open separate panels?
   - Recommendation (discretion area): Singleton, following ReviewPanel pattern. `PROverviewPanel.getOrCreate()` replaces content when a different PR is clicked — simpler lifecycle management.

3. **Renamed files: diff editor behavior**
   - What we know: `listFiles` returns `status: 'renamed'`, `filename` (new path), `previous_filename` (old path)
   - What's unclear: Should the diff title show "old → new" or just the new filename?
   - Recommendation: Show `#<prNumber> <new_filename> (renamed)` in the diff title. Fetch base content from `previous_filename`, head from `filename`.
