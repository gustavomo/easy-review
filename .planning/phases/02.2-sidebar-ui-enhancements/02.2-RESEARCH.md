## Summary

Phase 2.2 is a focused package.json contribution + thin TypeScript layer. The large majority of the work lives in `package.json` (command declarations, menu entries). The TypeScript changes are three narrow additions: (1) `contextValue` logic in `PRTreeItem`, (2) a `loadReview()` public method on `ReviewPanel`, and (3) two new command registrations in `activation.ts`.

All backing commands for the title bar buttons either already exist (`easyReview.viewAnalysis`, `easyReview.analyzePRHistory`) or are trivial one-liners (`easy-review.openSettings`). The `PRTreeItem` constructor change requires passing or querying a `StorageAdapter` — the provider already holds one but does not currently pass it to the item constructor. The cleanest approach is to keep `PRTreeItem` pure (no store dependency) and set `contextValue` inside `EasyReviewPRsProvider.refresh()`/`addPR()` after a store query.

The `ReviewPanel.loadReview()` method has a clear, already-working internal path: the `loadReview` webview message handler (VIEW-03) already calls `updateState({ status: 'complete', review })` + `postMessage({ type: 'loadReviewResult', review })`. The new public method repeats exactly that logic, plus `panel.reveal()` to bring the panel forward.

**Primary recommendation:** All changes are in four files — `package.json`, `PRTreeItem.ts`, `EasyReviewPRsProvider.ts`, `ReviewPanel.ts`, and `activation.ts`. No new files needed.

## Architecture Patterns

### Pattern 1: contextValue with `-hasReview` suffix

**What:** `PRTreeItem.contextValue` currently = `pr-${pr.state}` (e.g. `pr-open`). Adding `-hasReview` suffix produces `pr-open-hasReview`. The existing `when` clause `viewItem =~ /^pr-/` still matches both forms because both start with `pr-`. The new `when` clause for the "View Review" button uses `viewItem =~ /hasReview/` — matches only the suffix variant.

**Verified by reading package.json line 3238:**
```json
{
  "command": "easyReview.generateReview",
  "when": "view == easy-review.prList && viewItem =~ /^pr-/",
  "group": "inline"
}
```
`/^pr-/` matches `pr-open`, `pr-open-hasReview`, `pr-closed`, `pr-closed-hasReview`, `pr-merged`, `pr-merged-hasReview`. No conflict.

**New entry pattern:**
```json
{
  "command": "easy-review.viewReview",
  "when": "view == easy-review.prList && viewItem =~ /hasReview/",
  "group": "inline"
}
```

**Where to set contextValue:** `EasyReviewPRsProvider` holds the `StorageAdapter` reference but currently does not pass it to `PRTreeItem`. The safest approach is to keep `PRTreeItem` dumb (pure data object) and compute the contextValue in the provider before constructing the item, or add a `setContextValue()` method on `PRTreeItem`. Based on the current code pattern — constructor sets everything — the cleanest implementation is to add a `hasReview` parameter to the `PRTreeItem` constructor or a setter used right after construction:

```typescript
// In EasyReviewPRsProvider.refresh():
this.prs = prs.map(pr => {
  const hasReview = store.getReviews(pr.repoId, pr.prNumber).length > 0;
  return new PRTreeItem(pr, hasReview);
});
```

This requires `EasyReviewPRsProvider` to hold a reference to `store` — it currently does not. Two options:
- Pass `store` to `EasyReviewPRsProvider` constructor (breaking change to activation.ts instantiation call — simple fix)
- Module-level `getStore()` call inside `refresh()` (already available as `getStore()` from activation.ts)

**Recommended:** Pass `store` to `EasyReviewPRsProvider` constructor as an optional second argument, consistent with how `credentialStore` is injected.

### Pattern 2: view/title navigation group ordering

**What:** VS Code renders `navigation` group items right-to-left in the title bar. Items with explicit priority (`navigation@1`, `navigation@2`, `navigation@3`) are ordered by number. Lower numbers = leftmost.

**Evidence from package.json:** The upstream extension uses `navigation@1`, `navigation@2` etc. extensively (lines 2809–2954). The current easy-review title bar entries use plain `"group": "navigation"` (lines 2959, 2964) — they appear in document order.

**Decision from CONTEXT.md (D-05):** Use `navigation@1`, `navigation@2`, `navigation@3` to control order explicitly. Settings (most used) should be most accessible (leftmost). Proposed mapping:
- `navigation@1` — `easyReview.viewAnalysis` ($(book)) — leftmost
- `navigation@2` — `easyReview.analyzePRHistory` ($(history)) — middle
- `navigation@3` — `easy-review.openSettings` ($(settings-gear)) — rightmost

Note: VS Code renders navigation group left-to-right by ascending number, so `@1` is leftmost. This is confirmed by the upstream pattern: `navigation@1` for primary action, higher numbers for secondary.

The existing `easy-review.refreshPRList` and `easy-review.addPRByUrl` use plain `"navigation"` — they will remain unaffected by the numbered entries.

### Pattern 3: ReviewPanel.loadReview() public method

**What:** A new public method on `ReviewPanel` that loads an existing `StoredReview` and transitions the panel to the `complete` state without triggering AI generation.

**Existing infrastructure (verified by reading ReviewPanel.ts):**
- `handleWebviewMessage` case `loadReview` already does: parse `stored.parsedJson`, construct `ParsedReview`, call `updateState({ status: 'complete', review })`, call `postMessage({ type: 'loadReviewResult', review })` — lines 270-291
- `getOrCreate()` already reveals the panel if it exists — line 82-84

**New public method shape:**
```typescript
/** UI-01: Load an existing stored review into the panel without generating a new one. */
loadReview(stored: StoredReview): void {
  // Reveal panel (bring to front if already open)
  this.panel.reveal(vscode.ViewColumn.Two, false);
  
  const sections = JSON.parse(stored.parsedJson) as ReviewSection[];
  const review: ParsedReview = {
    id: stored.id,
    prNumber: stored.prNumber,
    repoId: stored.repoId,
    model: stored.modelUsed,
    createdAt: stored.createdAt,
    sections,
  };
  this.updateState({ status: 'complete', review });
  this.postMessage({ type: 'loadReviewResult', review });
}
```

This mirrors lines 278-290 of the existing `loadReview` message handler exactly. The import of `ReviewSection` is already available from `../../shared/types`.

### Pattern 4: easy-review.viewReview command

**What:** New command registered in `activation.ts` that:
1. Receives a `PRTreeItem` (or `StoredPR` from the tree item context)
2. Queries `store.getReviews(pr.repoId, pr.prNumber)`
3. Sorts by `createdAt` descending, takes index 0
4. Calls `ReviewPanel.getOrCreate(context, store).loadReview(latestReview)`

**Argument passing:** VS Code passes the tree item as the first argument when a command is triggered from a `view/item/context` menu entry. The command receives the `PRTreeItem` instance. Access the `StoredPR` via `item.pr`.

**Pattern (consistent with easyReview.generateReview at line 190 of activation.ts):**
```typescript
vscode.commands.registerCommand('easy-review.viewReview', (item) => {
  const currentStore = getStore();
  if (!currentStore || !item?.pr) { return; }
  const reviews = currentStore.getReviews(item.pr.repoId, item.pr.prNumber);
  if (reviews.length === 0) { return; } // button hidden by when clause, defensive guard
  const latest = reviews.sort((a, b) => b.createdAt - a.createdAt)[0];
  const panel = ReviewPanel.getOrCreate(context, currentStore);
  panel.loadReview(latest);
}),
```

### Pattern 5: easy-review.openSettings command

**What:** New command registered in `activation.ts` — one line.

```typescript
vscode.commands.registerCommand('easy-review.openSettings', () => {
  vscode.commands.executeCommand('workbench.action.openSettings', 'easyReview');
```

Note: `workbench.action.openSettings` accepts a search query string as the second argument. Passing `'easyReview'` filters the settings UI to the `easyReview.*` namespace. This pattern is already used at line 398 of activation.ts (`'easyReview.claudePath'`).

### Anti-Patterns to Avoid

- **Do not call `store.getReviews()` inside `PRTreeItem` constructor:** Would require passing the full store into every tree item. Keep `PRTreeItem` as a dumb data object — compute `hasReview` in the provider before constructing.
- **Do not use `startReview()` to load an existing review:** `startReview()` checks for existing reviews and prompts the user. For "view stored review" the correct path is the direct `loadReview()` method that skips generation entirely.
- **Do not add `view == easy-review.prList` check to the viewReview when clause:** The `view ==` guard is redundant for `viewItem` regex matches that are unique to this view's items. However, adding it is harmless and consistent with the existing `easyReview.generateReview` pattern — include it for defensive explicitness.
- **Do not use `retainContextWhenHidden: true`:** The panel already uses state-sync handshake pattern instead (confirmed in ReviewPanel constructor line 53). `loadReview()` posts a `loadReviewResult` message — the webview handles this exactly like the existing history dropdown selection.

## Common Pitfalls

### Pitfall 1: contextValue regex anchoring
**What goes wrong:** Using `viewItem == pr-open-hasReview` (equality) in a `when` clause instead of regex match. PR state varies (open/closed/merged), so equality would need three separate entries.
**Why it happens:** Developers default to `==` for simple comparisons.
**How to avoid:** Always use `viewItem =~ /hasReview/` (regex contains) for suffix-based matching. The regex operator `=~` in VS Code `when` clauses matches if the pattern appears anywhere in the string.
**Warning signs:** Button appears for one state but not others.

### Pitfall 2: contextValue not updated on review generation
**What goes wrong:** A user generates a review via "Generate Review". The PR now has a stored review, but the inline "View Review" button does not appear because `contextValue` was set at construction time and never updated.
**Why it happens:** `contextValue` is set once in the constructor; the tree item is not refreshed when a review is saved.
**How to avoid:** After `store.saveReview()` completes in `ReviewPanel.executeReview()`, fire a tree refresh for that specific PR tree item. This requires `ReviewPanel` to call `getProvider()?.updatePRContextValue(pr.repoId, pr.prNumber)` or fire a full refresh. Simplest: expose a `refreshPR(repoId, prNumber)` method on `EasyReviewPRsProvider` that finds the item, updates its `contextValue`, and fires `_onDidChangeTreeData(item)`.
**Warning signs:** "View Review" button invisible after generating a review until VS Code is restarted.

### Pitfall 3: panel.reveal() before postMessage
**What goes wrong:** Calling `postMessage()` before `panel.reveal()`. If the webview is hidden (not destroyed), it may not receive the message until it becomes active.
**Why it happens:** `retainContextWhenHidden: false` means the webview DOM is destroyed when hidden. On re-reveal, the webview re-mounts and sends a `ready` message, triggering `postStateSync()`. This means `loadReview()` must either (a) call `reveal()` first and rely on the state-sync handshake to restore `complete` state, or (b) call both `updateState()` and `postMessage()` after `reveal()`.
**How to avoid:** In `loadReview()`: call `this.panel.reveal()`, then call `updateState()` + `postMessage()`. The `postStateSync()` in the `ready` handler will also fire and send `stateSync` — but `stateSync` sends `this.currentState` which is already set to `complete` by `updateState()`, so this is consistent and harmless.
**Warning signs:** "View Review" opens an empty panel instead of showing the review.

### Pitfall 4: navigation group ordering direction
**What goes wrong:** Assuming `navigation@1` = rightmost. In VS Code, the `navigation` group renders items left-to-right by ascending number. `@1` is leftmost.
**Why it happens:** Some older VS Code documentation used right-to-left language.
**How to avoid:** Assign `@1` to the most-used action (leftmost visible). Per D-05, Settings should be rightmost (least intrusive) → assign it the highest number.
**Warning signs:** Buttons appear in reverse expected order.

### Pitfall 5: Missing command in package.json commands array
**What goes wrong:** Registering a command in `activation.ts` but forgetting to add it to `package.json`'s `contributes.commands` array. The command works from the Command Palette but icon/title may be missing, and menu contributions referencing it may fail validation.
**Why it happens:** Two places must be kept in sync.
**How to avoid:** For every `registerCommand()` call: add a corresponding entry in `package.json` `contributes.commands`. For `easy-review.viewReview` and `easy-review.openSettings` — both need entries with title, category, and icon.

### Example 5: EasyReviewPRsProvider — store injection and refresh

```typescript
// EasyReviewPRsProvider constructor
constructor(credentialStore?: CredentialStore, private store?: StorageAdapter) {
  this.credentialStore = credentialStore;
}

// refresh() with hasReview check
refresh(prs: StoredPR[]): void {
  this.prs = prs.map(pr => {
    const hasReview = this.store
      ? this.store.getReviews(pr.repoId, pr.prNumber).length > 0
      : false;
    return new PRTreeItem(pr, hasReview);
  });
  this._onDidChangeTreeData.fire(undefined);
}

// refreshPRContextValue() — called after review generation completes
refreshPRContextValue(repoId: string, prNumber: number): void {
  const item = this.prs.find(
    p => p.pr.repoId === repoId && p.pr.prNumber === prNumber
  );
  if (!item || !this.store) { return; }
  const hasReview = this.store.getReviews(repoId, prNumber).length > 0;
  item.contextValue = hasReview ? `pr-${item.pr.state}-hasReview` : `pr-${item.pr.state}`;
  this._onDidChangeTreeData.fire(item);
}
```

## Open Questions

1. **contextValue refresh after review generation**
   - What we know: The "View Review" button only appears when `contextValue` contains `-hasReview`. This value is set at tree item construction. After generating a review, the item needs refreshing.
   - What's unclear: Whether the planner should treat this as part of Phase 2.2 (because UI-01 implies the button appears after review generation too, not just after restart) or defer it.
   - Recommendation: Include `refreshPRContextValue()` in the plan for Phase 2.2. The user expectation is that clicking "Generate Review" followed by "View Review" works within the same session. This is a single method call in `executeReview()` after `store.saveReview()` completes — low effort, high value.

2. **addPR() in EasyReviewPRsProvider needs hasReview check too**
   - What we know: `addPR()` creates a new `PRTreeItem(pr)` without a `hasReview` argument. For newly added PRs this is always false (no reviews yet), so it is correct at the time of addition. But if the extension is restarted with existing reviews, `refresh()` handles this correctly via `store.getReviews()`.
   - What's unclear: Is there a path where `addPR()` is called with a PR that already has reviews? (Yes — if the user removes and re-adds a PR.) 
   - Recommendation: Update `addPR()` to also query `store.getReviews()` for consistency.
