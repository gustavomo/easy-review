## Summary

This phase upgrades the review webview panel from plain markdown rendering to rich visual treatment. Four independent enhancements are in scope: syntax highlighting via highlight.js (all sections), Mermaid SVG diagram rendering (Mermaid section only), dedicated visual components for Categorized Changes and Impact Analysis sections, and markdown table CSS styles.

The primary technical risks are (1) mermaid.js v11 dynamic chunk loading conflicting with VS Code's strict CSP — mitigated by Vite `manualChunks` consolidation and adding `unsafe-eval` to CSP `script-src`; (2) mermaid's ~75MB unpacked size (but Vite tree-shaking reduces the actual bundle to ~2–3MB for the dist artifact); and (3) marked v4's synchronous render path requiring the `marked-highlight` extension package rather than the old 3-arg async `highlight` callback.

The `FindingCard.tsx` severity badge pattern (border-left + inline badge) is the reference implementation to follow for category chips and impact badges. All VS Code CSS variables needed (`--vscode-charts-blue/red/green/purple`, `--vscode-list-hoverBackground`, etc.) are confirmed available in webviews.

**Primary recommendation:** Install `highlight.js@^11.11.1`, `marked-highlight@^2.2.3`, and `mermaid@^11.14.0` as webview dependencies; configure Vite to bundle mermaid as a single consolidated chunk; add `'unsafe-eval'` to CSP; implement new section components following the `FindingCard` pattern.

### Pattern 1: highlight.js Integration via marked-highlight (SYNCHRONOUS)

**What:** Configure marked globally with highlight.js so all `<code>` blocks in all sections get syntax highlighting.

**When to use:** Applied once at module level in ReviewDocument.tsx (or a shared `configureMarked.ts` module). Applies to all `marked(content)` calls project-wide.

**Example:**
```typescript
// Source: https://github.com/markedjs/marked-highlight (marked-highlight README)
import { marked } from 'marked';
import { markedHighlight } from 'marked-highlight';
import hljs from 'highlight.js';

marked.use(
  markedHighlight({
    emptyLangClass: 'hljs',
    langPrefix: 'hljs language-',
    highlight(code, lang) {
      // D-03: auto-detect when no language tag
      const language = hljs.getLanguage(lang) ? lang : 'plaintext';
      return hljs.highlight(code, { language }).value;
    },
  })
);
```

For D-03 (auto-detect), use `hljs.highlightAuto(code).value` when `lang` is empty:
```typescript
highlight(code, lang) {
  if (lang && hljs.getLanguage(lang)) {
    return hljs.highlight(code, { language: lang }).value;
  }
  return hljs.highlightAuto(code).value; // D-03: auto-detect
},
```

### Pattern 2: Mermaid SVG Rendering (ASYNC in useEffect)

**What:** Mermaid's `mermaid.render()` is async. Use a React `useEffect` to render the SVG after component mount; display a loading placeholder then swap in the SVG.

**When to use:** `MermaidDiagram` component, called from the `isMermaidSection` branch in ReviewDocument.tsx.

**Example:**
```typescript
// Source: https://mermaid.js.org/config/usage.html
import mermaid from 'mermaid';

// Initialize once at module level (idempotent)
const isDark = document.body.classList.contains('vscode-dark') ||
               document.body.classList.contains('vscode-high-contrast');
mermaid.initialize({
  startOnLoad: false,
  theme: isDark ? 'dark' : 'default', // D-08
  securityLevel: 'loose',
});

let mermaidIdCounter = 0;

export function MermaidDiagram({ source }: { source: string }) {
  const [svg, setSvg] = React.useState<string | null>(null);
  const [error, setError] = React.useState<string | null>(null);
  const id = React.useRef(`mermaid-${mermaidIdCounter++}`);

  React.useEffect(() => {
    let cancelled = false;
    mermaid.render(id.current, source)
      .then(({ svg: renderedSvg }) => {
        if (!cancelled) setSvg(renderedSvg);
      })
      .catch((err: Error) => {
        if (!cancelled) setError(err.message); // D-09: show error, don't crash
      });
    return () => { cancelled = true; };
  }, [source]);

  if (error) {
    return (
      <div style={{ color: 'var(--vscode-list-errorForeground)', padding: '8px 12px',
                    background: 'var(--vscode-inputValidation-errorBackground)',
                    border: '1px solid var(--vscode-inputValidation-errorBorder)',
                    borderRadius: '4px', fontSize: '12px' }}>
        Mermaid render error: {error}
      </div>
    );
  }
  if (!svg) {
    return (
      <div style={{ color: 'var(--vscode-descriptionForeground)', fontSize: '12px' }}>
        Rendering diagram...
      </div>
    );
  }
  return <div dangerouslySetInnerHTML={{ __html: svg }} />;
}
```

### Pattern 3: CategorizedChangesSection — Category Chips + Bullets

**What:** Parse `### Heading` lines as category names, collect following bullet items. Render each category as a colored chip badge + indented bullet list.

**Pattern (following FindingCard.tsx conventions):**
```typescript
// Reference: src/webview/FindingCard.tsx — border-left + uppercase badge label

const CATEGORY_COLORS: Record<string, string> = {
  feature: 'var(--vscode-charts-blue)',
  'bug fix': 'var(--vscode-charts-red)',
  bugfix: 'var(--vscode-charts-red)',
  refactor: 'var(--vscode-charts-purple)',
  test: 'var(--vscode-charts-green)',
  docs: 'var(--vscode-descriptionForeground)',
};
function getCategoryColor(name: string): string {
  const key = name.toLowerCase();
  for (const [k, v] of Object.entries(CATEGORY_COLORS)) {
    if (key.includes(k)) return v;
  }
  return 'var(--vscode-badge-background)'; // D-12 unknown/other
}
```

Parsing strategy: split `content` on lines; detect `###` headings as category starts; accumulate bullet lines (`-`, `*`, or numbered) until next heading or end.

Fallback (D-13): if no `###` headings found, `return <div className="easy-review-md" dangerouslySetInnerHTML={{ __html: marked(content) }} />`.

### Pattern 5: Vite Bundle Configuration for Mermaid

**What:** Mermaid v11 dynamically imports sub-chunks at runtime; VS Code webview CSP blocks these. Consolidate all mermaid chunks into a single bundle file.

**Required vite.webview.config.ts additions:**
```typescript
build: {
  chunkSizeWarningLimit: 4000, // mermaid adds ~2-3MB to bundle; suppress Rollup warning
  rollupOptions: {
    // ... existing input config ...
    output: {
      // ... existing output config ...
      manualChunks(id) {
        // Consolidate all mermaid-related code into a single chunk
        // This prevents dynamic loading attempts that CSP blocks
        if (id.includes('node_modules/mermaid') || id.includes('node_modules/dagre')) {
          return 'mermaid-bundle';
        }
      },
    },
  },
},
```

### Pattern 6: CSP Update for unsafe-eval

**What:** Mermaid uses `new Function()` internally; this requires `unsafe-eval` in `script-src`.

**Current CSP in ReviewPanel.ts `getWebviewHtml()`:**
```
script-src 'nonce-${nonce}' ${this.panel.webview.cspSource}
```

**Updated CSP (D-07):**
```
script-src 'nonce-${nonce}' ${this.panel.webview.cspSource} 'unsafe-eval'
```

**Security note:** `unsafe-eval` weakens the CSP but is required for mermaid. Since the webview only loads known bundled scripts (no user-controlled code), this is acceptable. Scope it narrowly to just `script-src`.

### Anti-Patterns to Avoid

- **Do NOT import an hljs theme CSS file (e.g. `import 'highlight.js/styles/github.css'`).** This overrides VS Code theme colors with hardcoded values — violates D-04. Use manual CSS var overrides scoped inside `.easy-review-md .hljs`.
- **Do NOT use `mermaid.init()` (deprecated in v10, removed trajectory in v11).** Use `mermaid.render()` instead.
- **Do NOT use `mermaid.run()` on page load.** This auto-processes `<code class="language-mermaid">` elements in the DOM, which conflicts with our controlled render approach. Use `startOnLoad: false` and call `mermaid.render()` explicitly.
- **Do NOT call `mermaid.initialize()` inside a component render function.** It must be called once at module level before any `render()` calls.
- **Do NOT reuse mermaid element IDs.** `mermaid.render(id, ...)` creates a temporary DOM element with that ID during rendering. Use a counter or uuid-style IDs.
- **Do NOT conflict with existing `.easy-review-md pre code` CSS rule.** The new hljs overrides must be additive: `.easy-review-md pre code.hljs { ... }` rather than replacing the existing rule.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Language detection for code blocks | Custom regex language guesser | `hljs.highlightAuto()` | highlight.js auto-detect considers token frequency across 190+ language signatures; any custom guesser will misidentify TypeScript as JavaScript or miss bash/yaml |
| Marked + hljs integration | Custom Renderer override | `marked-highlight` package | The synchronous 2-arg renderer integration is undocumented; `marked-highlight` handles the `langPrefix`, `emptyLangClass` and fallback correctly |
| SVG sanitization for mermaid output | Custom SVG sanitizer | None needed — trust mermaid output | mermaid runs in the same bundle as our code; mermaid output is trusted; adding a sanitizer would strip necessary SVG attributes |
| Mermaid theme detection | Custom VS Code API call | `document.body.classList.contains('vscode-dark')` | VS Code injects `vscode-dark`, `vscode-light`, or `vscode-high-contrast` class on `<body>`; this is the documented pattern used by all VS Code webview extensions |

**Key insight:** The highlight.js and mermaid ecosystems are mature enough that hand-rolling any piece of their core functionality (language detection, SVG rendering) produces inferior results while adding maintenance burden.

## Common Pitfalls

### Pitfall 1: Mermaid Dynamic Chunk Loading Blocked by CSP

**What goes wrong:** Mermaid v11 splits its diagram renderers into lazy-loaded chunks. At runtime the webview tries to `import()` these chunks from the webview origin. VS Code CSP blocks the request with `net::ERR_ACCESS_DENIED`. Diagrams never render.

**Why it happens:** Vite's default code-splitting behavior lets Rollup emit separate chunks for mermaid's diagram types. The webview's CSP doesn't allow dynamic `import()` from unknown sources.

**How to avoid:** Use `manualChunks` in `vite.webview.config.ts` to force all `node_modules/mermaid` code into a single chunk. This eliminates runtime dynamic imports.

**Warning signs:** Console errors mentioning `ERR_ACCESS_DENIED` or `Content Security Policy` when the MermaidDiagram component mounts; SVG container remains empty.

### Pitfall 2: marked v4 `highlight` Callback — Async vs Sync

**What goes wrong:** The `marked` docs show a 3-arg `highlight(code, lang, callback)` form. Calling `marked(content)` synchronously (as `dangerouslySetInnerHTML` does) never waits for the async callback — code blocks render unhighlighted.

**Why it happens:** The async 3-arg form only works when `marked(src, opts, callback)` is called with a callback. The synchronous `marked(src)` path uses the 2-arg Renderer.code form.

**How to avoid:** Use `marked-highlight` (which wraps the synchronous Renderer.code path correctly) rather than passing `highlight` to `marked.setOptions` directly.

**Warning signs:** `marked.setOptions({ highlight: fn })` appears to work but code blocks have no syntax classes in the rendered HTML.

### Pitfall 3: hljs CSS Class Missing from `pre code`

**What goes wrong:** highlight.js adds `.hljs` class and language-specific token classes to the `<code>` element. But the existing `.easy-review-md pre code { background: none; padding: 0; }` rule strips background from all `code` inside `pre` — including hljs's highlighted output. Result: token colors appear but background is wrong.

**Why it happens:** Existing CSS rule is intentionally aggressive to reset the nested `code` in `pre`. hljs injects its own background via `.hljs { background: ... }`.

**How to avoid:** Override `.easy-review-md .hljs` specifically with VS Code CSS vars:
```css
.easy-review-md .hljs {
  background: var(--vscode-textCodeBlock-background);
  color: var(--vscode-editor-foreground);
}
```
Then use token-specific overrides for keyword, string, comment, etc.

**Warning signs:** Code blocks render with correct token colors but the background flashes or shows double-background.

### Pitfall 4: Mermaid ID Collision

**What goes wrong:** `mermaid.render(id, ...)` creates a hidden DOM element with `id` during render. If two `MermaidDiagram` components use the same ID, mermaid throws or renders into the wrong element.

**Why it happens:** Using a static string like `'mermaid-diagram'` for the render ID. In theory only one Mermaid section exists per review, but defensive ID generation is cheap.

**How to avoid:** Use a module-level counter: `let counter = 0; const id = \`mermaid-${counter++}\`;` (generate once per component instance via `useRef`).

**Warning signs:** Second diagram renders blank or throws "Element already exists" error.

### Pitfall 5: Mermaid `initialize()` Called Multiple Times

**What goes wrong:** If `mermaid.initialize()` is called inside a React component body (not in a `useEffect` or at module level), it gets called on every re-render and resets internal mermaid state mid-render.

**Why it happens:** React components re-render on state changes (e.g., svg state transition from null → SVG string).

**How to avoid:** Call `mermaid.initialize()` once at module level in `MermaidDiagram.tsx`, outside the component function.

**Warning signs:** Console logs from mermaid appearing multiple times; diagrams flickering.

### Pitfall 6: `--vscode-charts-*` Variables Not Available in Older VS Code

**What goes wrong:** `--vscode-charts-blue` etc. return `undefined` in VS Code versions before they were introduced.

**Why it happens:** Chart color variables were added around VS Code 1.65. The project targets VS Code `^1.110.0` (package.json), so this is not a risk in practice.

**How to avoid:** Not applicable — `engines.vscode` is `^1.110.0`, well past 1.65. All `--vscode-charts-*` variables are safe to use.

### mermaid.render() with React useEffect

```typescript
// Source: https://mermaid.js.org/config/usage.html — render() API
import mermaid from 'mermaid';
import React from 'react';

// Init once at module level (D-08: dark/light theme detection)
const isDark = typeof document !== 'undefined' &&
  (document.body.classList.contains('vscode-dark') ||
   document.body.classList.contains('vscode-high-contrast'));

mermaid.initialize({
  startOnLoad: false,
  theme: isDark ? 'dark' : 'default',
  securityLevel: 'loose',
});

let _counter = 0;

export function MermaidDiagram({ source }: { source: string }) {
  const [svg, setSvg] = React.useState<string | null>(null);
  const [error, setError] = React.useState<string | null>(null);
  const idRef = React.useRef<string>(`mermaid-${_counter++}`);

  React.useEffect(() => {
    let active = true;
    mermaid.render(idRef.current, source).then(({ svg: out }) => {
      if (active) setSvg(out);
    }).catch((err: Error) => {
      if (active) setError(err.message);
    });
    return () => { active = false; };
  }, [source]);

  if (error) {
    return (
      <div className="mermaid-error">Diagram error: {error}</div>
    );
  }
  return svg
    ? <div dangerouslySetInnerHTML={{ __html: svg }} />
    : <div className="mermaid-loading">Rendering diagram...</div>;
}
```

| `mermaid.mermaidAPI.render()` | `mermaid.render()` (top-level) | mermaid v10 | `mermaidAPI` sub-object is legacy; use top-level |

**Deprecated/outdated:**
- `marked.setOptions({ highlight: fn3args })`: Works for async callback form but not for the synchronous `marked(src)` call path. Use `marked-highlight` instead.
- `mermaid.init()`: Deprecated in v10, will be removed. Use `mermaid.render()`.
- `hljs.highlightBlock()` and `hljs.initHighlightingOnLoad()`: Removed in hljs v11. The library no longer provides DOM-scanning APIs — you must call `hljs.highlight()` or `hljs.highlightAuto()` explicitly.

## Open Questions

1. **Lazy vs. eager mermaid import**
   - What we know: mermaid adds significant bundle size; `vite.webview.config.ts` currently has no `chunkSizeWarningLimit` and will warn at default 500kB threshold
   - What's unclear: Whether Vite's dynamic `import('mermaid')` from within a `useEffect` interacts safely with the `manualChunks` consolidation, or if it creates a new chunk
   - Recommendation: Eager-load by default (simpler, avoids dynamic import complexity that was the root cause of the CSP issue); add `chunkSizeWarningLimit: 4000` to suppress the Rollup warning. Revisit lazy-load only if build times become problematic.

2. **Whether to parse markdown in components or in ReviewParser.ts**
   - What we know: ReviewParser.ts is the extension host module (runs in Node); CategorizedChangesSection and ImpactAnalysisSection are webview components (run in browser); `ReviewSection` type only has `content: string`
   - What's unclear: Whether pre-parsing in ReviewParser.ts would make the section type richer (e.g., `categories: Category[]`) without requiring a shared types change
   - Recommendation (Claude's Discretion): Parse markdown inside the components. Avoids changing `ReviewSection` type and shared types, keeps the components self-contained, and the parsing logic is simple (regex on `###` headings).
